You are editing **Cabinet Vision User Created Standards**. The files in this folder are not ordinary
source files: each one is a mirror of a row in the `UCS` table of the SQL database
**{{DATABASE}}** on **{{SERVER}}**.

Read this whole file before your first edit. The rules below are not style preferences — breaking
them either loses work or pushes code that Cabinet Vision cannot run.

## The seven rules

1. **Saving a file here writes straight to the live database.** A file watcher pushes every save to
   `UPDATE UCS SET Code`. There is no staging step, no undo and no git history — this folder ignores
   itself (`.gitignore` contains `*`). Treat every write as a change to production data. Do not make
   speculative or bulk edits "to see what happens".

2. **You cannot create a UCS.** Writing a new file into `ucs/` or `lib/` does *nothing* — it is not
   in `manifest.json`, so the watcher ignores it and logs a message to an output channel you cannot
   see. The file will sit on disk looking like a success while the database never hears about it.
   New standards must be created inside Cabinet Vision (Utilities → User Created Standards → New).
   If asked to create one, say so rather than writing the file.

3. **You cannot delete or rename a UCS.** Deleting a file does not delete the row; renaming one
   breaks the manifest entry that links the file to its row. Both are done in Cabinet Vision.

4. **Never touch the sentinel lines.** Every mirrored file opens with a four-line generated header —
   the lines beginning `//~` or `;~` — and a `.ucs.js` file also has a wrapper line before the code
   and a matching one at the very end. None of it is part of the standard:

   | file | header | opens | closes |
   |---|---|---|---|
   | `ucs/<Name>.ucs.js` | 4 × `//~` | `(function () {` | `})();` |
   | `lib/<Name>.ucs.js` | 4 × `//~` | a JSDoc block, then `const _<name> = new class <Name>Library {` | `}();` |
   | `ucs/<Name>.ucsm` | 4 × `;~` | — | — |

   The wrappers exist so VS Code's TypeScript service scopes the file the way Cabinet Vision executes
   it. A library's JSDoc block is generated with the wrapper and is not documentation of the library:
   it is what the editor shows whoever hovers `_<name>` elsewhere. Edit only the lines *between* the
   sentinels. Writing anything below the closing sentinel is the one
   failure the extension cannot recover from: the closing line stops being recognised and gets pushed
   into the database as part of your code, and Cabinet Vision then fails to parse the standard.

5. **The `For Each` line and the filters are not always code.** For **UCS:M** the `For Each` is the
   first statement of the code and you edit it here. For **UCS:JS** it is a *property* of the
   standard, set in the UCS Manager UI — there is no `For Each` in the JavaScript, and adding one is
   an error. The same is true of UCS:JS public variables, and of every filter tab (assembly class,
   construction method, end types). If a change belongs on one of those, say so; you cannot make it
   from here.

6. **The two languages are not interchangeable.** `.ucsm` is UCS:M, Cabinet Vision's own macro
   language. `.ucs.js` is UCS:JS, JavaScript, available from CV 2024.1. Never rewrite one as the
   other — the file extension is bound to the row's `MacroType` column, and changing the language of
   an existing standard is done in Cabinet Vision, not by editing the file.

7. **Match the surrounding code.** These standards are maintained by cabinet makers, not by
   full-time programmers, and they are read far more often than they are written. Follow the
   conventions already in the file you are editing.

## Before you write UCS:JS

Read [`cv-api.d.ts`](cv-api.d.ts) — it is the complete API surface, generated from Cabinet Vision's
own documentation plus this database, and it carries descriptions and examples as JSDoc. If a
method, constant or material name is not in that file, it does not exist. Do not guess at API names;
the runtime is not a browser and not Node.

Then read [`ucsjs-reference.md`](ucsjs-reference.md) for the rules that a type declaration cannot
express — the execution model, why `var` is not a parameter, where public variables come from, and
why `==` on two measurements is a bug.

The short version:

- `_this` is the object the standard is running against; `_cab` is the assembly that owns it.
- The file body is a **function body**, so a top-level `return` is legal and is the normal way to
  bail out early. Do not "fix" one.
- JavaScript is case sensitive; `_this.Dx` is not `_this.DX`.
- A string handed to `Evaluate` or assigned to a parameter is a *Cabinet Vision* equation, evaluated
  by CV, and follows UCS:M rules — not JavaScript ones.
- Libraries in `lib/` are reachable from any standard as `_<lowercase name>`, e.g. a library named
  `Helpers` is called as `_helpers.Method()`. That global is declared by the sentinel line.

## Before you write UCS:M

Read [`ucsm-reference.md`](ucsm-reference.md). UCS:M looks like BASIC but is not: it has no user
functions, no local variables and no arrays, every assignment writes a parameter onto an object in
the model, and the first line of every standard must be a comment.

## When you are done

- Say which standards you changed, by name, and that the changes are already in the database.
- If a change needs something you cannot do from here — a new standard, a filter, a public variable,
  a `For Each` on a UCS:JS — list those steps for the user to do in Cabinet Vision.
- Do not claim a new standard was created. See rule 2.
